# 纯插件的在线播放加速（extension/）

## 结论
只装一个 Chrome 插件、不需要本地程序，在线播放加速的效果和以前 bilidl-web 的本地代理（[PLAYBACK.md](https://github.com/Yangxiamao/bilidl/blob/main/docs/PLAYBACK.md)，已删除）相当。真实 B 站播放器锁定 4K（2880x2160），1x → 2x → 跳到 60% → 3x：

| 阶段 | 直连 | 插件（中档） |
|---|---|---|
| 1x 25 秒 | 不卡，缓冲最少只剩 3 秒 | 不卡，缓冲 ≥ 32 秒 |
| 切到 2x 30 秒 | 卡 4 次共 10.2 秒 | 不卡，缓冲 ≥ 70 秒 |
| 跳到 60% 后 2x 25 秒 | 一直卡住，只播了 1 秒 | 卡 1 次 0.4 秒 |
| 切到 3x 25 秒 | 一直卡住 | 不卡，缓冲 ≥ 69 秒 |

- 播放器自己发出的视频分段请求是 0 个：`document_start` 的 MAIN world 脚本确实早于播放器，所有分段都由插件返回，没有一次退回直连。
- 不锁画质时，开了插件后播放器的自适应码率会自己切到 4K（直连时停在 480x360）。
- 只需要 `storage` 权限，没有 host 权限，没有远程代码，适合上架 Chrome Web Store。

## 怎么装（开发版）
普通用户从 Releases 下载打包好的 zip，见 [README](../README.md#安装)。从源代码装：

1. `node tools/build_ext.mjs`，生成 `dist/bilifast/`（`--zip` 时另外打一个上架用的 zip）。
2. Chrome 打开 `chrome://extensions`，打开「开发者模式」，「加载已解压的扩展程序」选 `dist/bilifast`。
3. 打开（或刷新）B 站视频页。点工具栏上的插件图标看状态、开关、切换档位；图标角标是「播放器缓冲 + 插件预读」领先的秒数（取整到 10 秒），关闭时显示「关」。

从 v1.0.x 升级的：旧的下载插件（chrome-extension/）里的播放加速已经去掉，到 `chrome://extensions` 点它的刷新按钮即可，两个插件可以同时装、互不影响。

## 设计
和已删除的旧方案（bilidl-web 本地代理，[PLAYBACK.md](https://github.com/Yangxiamao/bilidl/blob/main/docs/PLAYBACK.md)）是同一套算法，只是从 Python 线程搬到了页面里的异步并发；为什么页面里并发就能提速见 [EXTENSION_ONLY.md](EXTENSION_ONLY.md)。

### 文件
| 文件 | 作用 |
|---|---|
| `shared/hosts.js` | 节点列表、按实测速度排序（`HostHealth`）、挑节点。以后下载插件也用。节点列表和失败冷却规则与 `bilidl.py` 一致，挑节点的规则见下文 |
| `extension/src/engine.js` | 分块缓存和调度（从旧的本地代理 `bilidl_play.py` 移植）。不碰 DOM 和 XHR，fetch 从外面传进来，可以离线测 |
| `extension/src/hook.js` | 接管播放器的 XHR，和 bridge 通信 |
| `extension/bridge.js` | ISOLATED world 内容脚本：设置从 `chrome.storage` 转给页面，状态转给弹出页，通知后台更新角标 |
| `extension/background.js` | 只设置角标 |
| `extension/popup.*` | 开关、档位、状态 |
| `extension/store/` | 图标的 SVG 源文件、商店图片的 HTML 源文件，以及上架 Chrome 应用商店用的文字（`listing.md`）、隐私说明（`PRIVACY.md`）和待办清单（`CHECKLIST.md`）。不打进插件 |
| `tools/make_icons.mjs` | 用无头 Chrome 把 `store/` 里的 SVG、HTML 渲染成 `icons/*.png` 和商店图片 |
| `tools/build_ext.mjs` | 把 `shared/hosts.js`、`engine.js`、`hook.js` 去掉 import/export 后合成一个 IIFE 的 `page.js`（MAIN world 和页面共用全局作用域，不能往上面挂变量），复制其余文件到 `dist/bilifast/` |

### 权限
只有 `storage`，没有 host_permissions。内容脚本只在 `www.bilibili.com` 的 `/video/`、`/list/`、`/bangumi/play/`（含 `/zh-Hans/` 这类语言前缀）上运行。请求从 bilibili.com 页面发出，CDN 本来就放行这个来源的 CORS。页面通过事件只能影响它自己那个标签页：bridge 不接受页面写设置。

### 接管（hook.js）
`page.js` 以 `"world": "MAIN"`、`document_start` 注入，在播放器脚本之前把 `window.XMLHttpRequest` 换成子类：
- 只接管同时满足的请求：GET、异步、`responseType = "arraybuffer"`、`Range: bytes=a-b`（两端都有）、`https://upos-*.bilivideo.com` 或 `upos-*.akamaized.net` 上的 `.m4s`、开关开着。其余全部原样调用原来的 `send`。播放器将来改用 fetch 或 Worker 时碰不到，自然就是直连。
- 接管后交给 engine，拿到数据在实例上伪造 `readyState`（2 → 3 → 4）、`status`（206）、`response`、`getResponseHeader` 等，按原生顺序派发 `loadstart`、`readystatechange`、`progress`、`load`、`loadend`。播放器 `abort()` 时派发 `abort`；设了 `xhr.timeout` 时到点派发 `timeout`；重新 `open()` 时悄悄丢掉进行中的请求，和原生一样。
- engine 出任何错（所有节点都失败、等待超过 30 秒、起点超出文件末尾等）都改调原来的 `send`，等于退回直连；超出末尾的请求因此拿到 CDN 真正的 416。

### 缓存和调度（engine.js）
逐条对应旧的本地代理 `bilidl_play.py`（[PLAYBACK.md](https://github.com/Yangxiamao/bilidl/blob/main/docs/PLAYBACK.md)）：
- 1 MB 分块，以 URL 路径为键，和节点、签名无关；同一块排队或下载中时只有一个任务。
- 两级优先级：播放器在等的块（一个请求覆盖的块一起排，最多 32 块）和预读。普通并发池先拿紧急块再拿预读；另有一个只拉紧急块的小池子，预读占满时也不用排队。
- 2.5 秒对冲：紧急块 2.5 秒没拉完就向另一个节点再拉一份，先到的生效并**取消另一路**（Python 版不取消）。对冲不占并发名额。
- 单次拉取 5 秒收不到新数据算超时（按读到的每一段数据重置计时）。
- 挑节点：按单个请求速度的滑动平均排序；预读 85% 在最快 3 个之间随机、15% 给其余节点；紧急块用测过的最快节点；akamai 不参与排序，只在第 3 次重试时用；连续失败 3 次冷却 60 秒。
- 预读窗口 = clamp(最近 20 秒的取数速度 × 预读秒数, 32 MB, 窗口上限)，开始和跳转后 30 秒内按 20 秒算，追上预读时下限翻倍。
- 跳转：没命中、又不在「当前位置 − 2 MB ~ 当前位置 + 窗口」时作废旧窗口里没开始的预读；回头再要已缓存的数据不算跳转。
- 内存：每个标签页有上限；超出时**不再开始新的预读**（Python 版队列里的预读还会接着拉），先丢播放位置之前的块，再丢 30 秒没用过的资源；闲置 10 分钟释放；关闭加速时立刻全部释放。

### 三档配置
弹出页里选，默认「中」。数值先按下面的实测定。

| 档位 | 并发（普通 + 只拉紧急块） | 预读秒数 | 预读窗口上限 | 每个标签页的内存上限 |
|---|---|---|---|---|
| 低 | 6 + 3 | 60 | 128 MB | 256 MB |
| 中 | 12 + 4 | 90 | 256 MB | 512 MB |
| 高 | 24 + 6 | 120 | 512 MB | 1 GB |

单个节点上 16 个并发约 32~44 MB/s（[EXTENSION_ONLY.md](EXTENSION_ONLY.md)），4K 3 倍速约需 6 MB/s，所以低档也够用；档位主要决定预读多远、占多少内存。

## 验收
2026-10-29，作者的网络（日本），登录账号，BV1bE41127s6（4K，8.5 GB，平均码率 1.97 MB/s），无头 Chrome 156，静音。

### 离线：`node tests/play_engine_test.mjs`，全部通过
各种 Range（跨块、不对齐、文件末尾、超出末尾截断、完全超出）、8 个请求落在同一块只拉一次、只给 akamai 链接时换节点、最快节点卡住时对冲、全部出错时抛异常、播放器取消、预读和跳转判断、内存上限、关闭时释放、挑节点规则。

### 正确性：`node tests/play_ext_test.mjs correct`，全部通过
真实页面里用 XHR 发 Range，接管返回的数据和直连逐字节一致（SHA-256）：初始化段、跨块、不对齐跨三块、4K 一个分段（约 6 MB）、文件最后 1000 字节、超出末尾截断、音频、只给 akamai 链接、8 个并发请求落在同一块。完全超出文件时改发原请求，拿到 CDN 的 416。`responseType = blob`、没有 Range、`bytes=N-` 都原样放行。用 CDP 让插件的 fetch 全部失败时，请求退回直连，数据一致。

### 挑节点：为什么从「前 3 名随机」改成「按速度加权」
第一版照搬 Python 的规则：预读块在最快的 3 个节点之间均匀随机分，15% 随机给其余节点。这天各节点速度差了上百倍（aliov 单个请求约 20 MB/s，08ct / hw / hwb 只有 0.1~0.4 MB/s，而且是一直慢慢给数据，不触发 5 秒超时）。按块数平均分时，并发几乎全耗在慢节点上：模拟播放器的总拉取速度只有 2~8 MB/s，预读领先一直接近 0，2x 和 3x 都卡。改成下面这样以后，同样的场景四个阶段都不卡：
- 预读只在「速度不低于最快节点 30%」的节点之间按速度加权分；
- 没测过的和慢的节点只拿 10% 的机会试探，而且同一时间最多 1 个；
- 一块拉了 10 秒还没完也算失败，慢连接最多占一个并发 10 秒；
- 一个节点都没测过时，紧急块随机分到不同节点（第一版全压在列表第一个上，那个节点正好慢，起播用了 8.5 秒）。

### 番剧页、列表页、切换分 P 和清晰度：`node tests/play_ext_test.mjs nav`，全部通过
2026-10-29，同样的环境，中档、2 倍速。每个场景先播 40 秒（过了预读的热身期），再用播放器自己的接口切换（`player.next()`、`player.requestQuality()`；番剧页的 `next()` 不换集，改成点选集列表里的下一集），接着播 30 秒。

| 场景 | 切换后 | 旧的流在切换后又拉了 |
|---|---|---|
| 切换分 P（BV1Q24y1j7YT P1 → P2） | 0.7 秒开始播放，不卡，360P → 1080P | 0 块 |
| 切换清晰度（1080P+ → 1080P） | 0.2 秒，不卡 | 0 块 |
| 列表页（UP 主的视频列表，下一个视频） | 1.8 秒，卡 1 次 1.0 秒 | 0 块 |
| 番剧页（邻座的怪同学 第 1 集 → 第 2 集） | 0.7 秒，不卡 | 0 块 |

- 四个场景都是播放器自己发出的 m4s XHR 为 0、退回直连 0、未接管 0：单页跳转（切分 P、列表里的下一个、换集）后 `page.js` 还在，新的流照样被接管。
- 番剧页的播放器对象和视频页一样（`window.player`），请求方式也一样；正片之外的片头等流也被接管。
- 原来担心切换后旧的流排着的预读还会继续拉、和新的流抢并发（预读队列是全局先进先出的），实测没有发生：切换时旧的流的预读已经拉完，切换后 0 块，所以没有改调度。
- 卡顿只算「画面没在走、而且前面缓冲不到 1.5 秒」：无头 Chrome 软件解码 4K 2 倍速时画面偶尔会顿一下，那时缓冲是满的，不是网络问题。

## 没做 / 已知问题
- 后台标签页里定时器会被限流，对冲和超时会变迟钝（有声音的标签页不受「密集限流」影响）。
- 嵌入播放器（`player.bilibili.com`）、直播不在范围内。
- 每个标签页各自一份缓存和节点测速，开多个视频页时内存按标签页叠加。
- 统计上报（`data.bilibili.com`）的网址参数里也会带 `.m4s`，只按路径判断，不算进「未接管」。
